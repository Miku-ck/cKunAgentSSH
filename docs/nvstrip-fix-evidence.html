GPU 卡行条带「空的 / 不会动」· 缺陷修复证据

本页已作废（2026-09-21 补注）：本页证明的是 NvStrip（竖向历史条带） 的「函数型 prop 默认值陷阱」已被修复 —— 该结论仍然成立，且已由 NvGauge.test.ts 继续守护。但 NvStrip 组件本身已被删除： 同日后续改动把全部条状图统一成了「12px 横向进度条 + 4px 趋势薄条」（NvGauge.ts）， 所以本页展示的竖向形态不再代表当前实现。当前实现的真实渲染与断言见 docs/nvgauge-evidence.html。本页保留作为那次缺陷的完整证据链。

你报的现象：下方每张卡的 MEM / UTL 条带是空的、不动；上面 System 区却正常。 本页所有条带的 HTML 都是真实 NvStrip 组件的 SSR 输出 （esbuild 从 src/ 打包后渲染），不是手抄标记。 4 卡的当前值为实测，历史序列是构造的示意（你只给了当前值），末点已对齐实测值。

根因一句话：条带子组件用了 cls: { type: Function, default: () => blkCls } 这种「函数型 prop + 工厂式默认值」的写法。Vue 在 type: Function 时不会把默认值当工厂调用 （resolvePropValue 只在 opt.type !== Function 时执行 defaultValue.call()）， 于是 cls 是那个包装函数本身 → cls(v) 返回一个函数 → normalizeClass 对函数返回空串（它只认 string / array / 普通对象）→ 柱子渲染成 class=""，没有任何背景色规则命中，看起来就是一条空轨。
为什么难发现：GPU 卡行的调用点没传 :cls（走默认值）→ 中招； System 区的调用点显式传了 :cls → 正常。同一份组件、同一份数据， 只因为调用点不同而「一半好一半坏」，所以第一眼会误以为是数据没采到。 下面第 3 节把这两条路径的原始 HTML 摆在一起。
